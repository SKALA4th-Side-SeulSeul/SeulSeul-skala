## D-005 — 커밋 메시지 형식

- 날짜: 2026-09-14
- 상태: 확정
- 내용: 커밋 메시지는 `<타입>: <한국어 설명>` 형식으로 쓰고, 한 커밋에는 하나의 목적만 담습니다.

| 타입 | 용도 | 예시 |
| --- | --- | --- |
| `feat` | 기능 추가·변경 | `feat: 체크리스트 배정 서비스 추가` |
| `fix` | 버그 수정 | `fix: 마감일 없는 공지의 알림 누락 수정` |
| `refactor` | 동작 변경 없는 구조 개선 | `refactor: 공지 채널 검증 로직 분리` |
| `test` | 테스트만 추가·수정 | `test: 중복 체크리스트 생성 테스트 추가` |
| `docs` | 문서만 수정 | `docs: 커밋 규칙 정리` |
| `chore` | 설정, 의존성, 스크립트 등 | `chore: Ruff 설정 추가` |

- 이유: 제목만으로 변경 종류를 구분하고, 설명은 팀이 쓰는 언어로 통일하기 위함입니다.
- 포기한 대안:
  - `Add checklist ...`처럼 영어 동사로 시작하는 형식(첫 커밋의 `COLLABORATION.md`): 실제 커밋 방식과 달라 바꿨습니다.
  - `add` 타입: `feat`, `test`, `docs`, `chore`와 경계가 겹쳐 두지 않습니다.

## D-008 — check.sh가 개발 환경을 자동 준비

- 날짜: 2026-09-14
- 상태: 확정
- 내용: `./scripts/check.sh`는 검증 전에 `.venv`를 Python 3.11로 준비합니다. `.venv`가 없거나 버전이 다르면 다시 만들고, pytest·ruff가 없거나 `pyproject.toml`이 바뀌었으면 `pip install -e '.[dev]'`를 다시 실행합니다. Python 3.11 자체는 설치하지 않고 안내만 합니다.
- 이유: 3.11이 아닌 Python으로 만든 `.venv`나 의존성 미설치 때문에 팀원 환경에서 2단계 테스트가 `No module named pytest`로 실패했기 때문입니다.
- 포기한 대안: 실패 시 안내 메시지만 출력. 원인을 사람이 해석하고 명령을 직접 실행해야 해서 채택하지 않았습니다.
- 결과: 에이전트는 모듈 누락 오류를 `.venv` 직접 수정이 아니라 `./scripts/check.sh` 재실행으로 해결합니다.

## D-011 — AI 분석 결과와 실패 처리

- 날짜: 2026-09-14
- 상태: 확정
- 내용:
  - AI는 `title`, `summary`, `deadline_at`, `deadline_source_text`를 포함한 JSON 객체를 반환합니다.
  - `title`은 체크리스트 제목, `summary`는 학생이 해야 할 행동을 포함한 요약, `deadline_at`은 ISO 8601 형식의 마감 시각, `deadline_source_text`는 마감일 판단에 사용한 원문의 표현입니다.
  - 기준 시간대는 `Asia/Seoul`이며, 날짜만 있고 시각이 없으면 해당 날짜의 `23:59`로 처리합니다.
  - 공지에는 마감일이 정확히 하나 존재한다는 제품 전제를 둡니다. 모든 필드는 필수이며, JSON 형식 오류·빈 필드·해석할 수 없는 마감일·여러 마감일은 분석 실패로 처리합니다.
  - `deadline_source_text`가 실제 원문에 존재하는지 검증해 원문에 없는 마감일 생성을 막습니다.
  - 분석에 실패하면 오류 원인을 포함해 최초 호출을 포함한 최대 3회까지 시도합니다. 계속 실패한 신규 공지는 체크리스트를 생성하거나 DM을 보내지 않고 `processing_failed` 상태와 실패 원인을 기록합니다.
  - 기존 공지의 수정 내용을 분석하다 실패하면 기존 체크리스트를 유지하고 갱신하지 않습니다.
- 이유: AI의 자유 형식 응답과 잘못된 마감일이 학생의 체크리스트와 알림으로 바로 전달되는 것을 막기 위함입니다.

## D-012 — 공지 식별, 링크 중복과 원본 변경

- 날짜: 2026-09-14
- 상태: 확정
- 내용:
  - Slack 원본 메시지는 `workspace_id + channel_id + message_ts` 조합으로 식별합니다.
  - URL을 정규화한 `canonical_url`을 별도의 링크 중복 판별 키로 사용합니다. 불필요한 쿼리 문자열, fragment와 마지막 `/`의 차이는 제거합니다.
  - 서로 다른 Slack 메시지라도 `canonical_url`이 같으면 이미 처리한 링크로 보고 체크리스트를 추가 생성하지 않습니다.
  - 원본 메시지가 수정되면 D-009의 채널·URL 조건을 다시 검증합니다. AI 분석에 성공하면 기존 공지와 학생별 체크리스트의 제목·요약·마감일을 갱신하되 학생별 완료 상태는 유지합니다.
  - 수정된 원본이 더 이상 처리 조건을 만족하지 않거나 원본 메시지가 삭제되면 연결된 공지와 학생별 체크리스트를 삭제 상태로 전환하고 예정된 DM 알림도 취소합니다.
  - 원본 수정 내용의 AI 분석에 실패하면 기존 데이터를 유지합니다.
- 이유: Slack 이벤트의 중복 수신과 같은 링크의 반복 게시로 체크리스트가 중복 생성되는 것을 막고, 원본 공지의 변경을 학생별 체크리스트에 일관되게 반영하기 위함입니다.

## D-013 — AI 제공자 선택

- 날짜: 2026-09-14
- 상태: 확정 (개발 단계)
- 범위: AI 제공자와 모델 선택만 다룹니다. AI 응답 형식·검증·재시도·실패 처리는 D-011을 따릅니다.
- 내용: AI 호출은 OpenAI 호환 `/chat/completions` 클라이언트 하나로 하고, `AI_PROVIDER`로 `nvidia`(NVIDIA Build API) 또는 `ollama`(로컬 LLM)를 고릅니다. 비워 두면 AI를 쓰지 않습니다. 모델 이름은 `NVIDIA_MODEL`, `OLLAMA_MODEL`로 지정하고 코드에 고정하지 않습니다.
- 이유: API 키가 없는 개발자도 로컬 LLM으로 테스트할 수 있고, 두 제공자 모두 OpenAI 호환 API를 지원하기 때문입니다.
- 포기한 대안 (로컬 연결 테스트 1회 기준): `qwen3.5:2b`는 추론 과정만 출력해 요약이 비었고, `qwen2.5:0.5b`는 요약 형식을 지키지 못했습니다. 개발 기본 모델은 `llama3.2`를 씁니다.
- 결과: `nvidia`를 쓰면 공지 원문이 외부로 전송되므로, 실제 워크스페이스 운영 전에 데이터 정책을 정해야 합니다.

## D-014 — 링크 하나를 공지 하나로 처리

  - D-012의 Slack 원본 메시지 단위 처리 방식을 보완해, D-009의 조건을 만족하는 링크 하나를 공지 하나로 처리합니다.
  - 한 Slack 메시지에 처리 가능한 링크가 여러 개 있으면 링크마다 별도의 공지와 학생별 체크리스트를 생성합니다.
  - 원본 메시지는 `workspace_id + channel_id + message_ts`로 식별하고, 개별 공지는 이 값에 `canonical_url`을 더해 식별합니다.
  - 학생에게 제공할 `original_url`은 원문 그대로 저장합니다. 중복 판정용 `canonical_url`은 query string, fragment와 마지막 `/`를 제거해 만듭니다.
  - 단축 URL과 단축 URL이 가리키는 원본 URL은 자동으로 같은 링크라고 판정하지 않습니다.
  - 원본 메시지가 수정되면 유지·추가·제거된 링크를 비교합니다. 유지된 링크의 공지는 갱신하고, 추가된 링크는 새 공지로 처리하며, 제거된 링크의 공지와 체크리스트는 삭제 상태로 전환합니다.
- 이유: 한 메시지에 서로 다른 제출 링크가 함께 올라와도 각 할 일을 독립적으로 완료하고 알림 받을 수 있게 하기 위함입니다.
- 결과: D-012의 `canonical_url` 중복 정책은 개별 링크마다 적용합니다.

## D-016 — PostgreSQL과 최소 데이터 모델

- 날짜: 2026-09-14
- 상태: 확정
- 내용:
  - 데이터베이스는 PostgreSQL을 사용합니다.
  - 애플리케이션과 데이터 접근 코드는 Python으로 작성하고, Python ORM인 SQLAlchemy와 Python 기반 마이그레이션 도구인 Alembic을 사용합니다.
  - 최소 영속 엔터티는 `students`, `notices`, `checklists` 세 종류로 분리합니다. 학생 한 명에게 여러 체크리스트가 배정되고, 공지 하나가 여러 학생의 체크리스트 원본이 되므로 각 관계를 외래 키로 표현합니다.
  - AI 처리 실패 전용 테이블은 만들지 않습니다. `notices`에 `processing_status`, `retry_count`, `last_error`, `next_retry_at`을 두어 처리 상태와 최근 실패를 관리합니다.
  - Slack 원본이 삭제되거나 처리 조건에서 제외되면 공지와 체크리스트를 물리적으로 지우지 않고 삭제 상태와 `deleted_at`을 기록합니다.
  - 학생이 알림 수신을 해지하면 해당 학생의 개인 정보와 개인별 체크리스트 데이터는 보존하지 않습니다. 여러 학생이 공유하는 원본 공지 데이터는 유지합니다.
- 이유: 공지·학생·개인별 완료 상태의 관계는 분리하되, AI 실패만을 위한 테이블은 만들지 않아 초기 스키마를 단순하게 유지하기 위함입니다.

## D-017 — NVIDIA Build 호출 기본값과 실패 복구

- 날짜: 2026-09-14
- 상태: 확정
- 내용:
  - 운영 환경에서는 D-013의 `nvidia` 제공자와 NVIDIA Build의 `https://integrate.api.nvidia.com/v1/chat/completions` 엔드포인트를 사용합니다. Ollama는 API 키가 없는 로컬 개발 대안으로 유지합니다.
  - 초기 `NVIDIA_MODEL`은 `qwen/qwen3.5-122b-a10b`로 정하고 코드에 고정하지 않습니다. 실제 한국어 공지 표본 테스트에서 기준을 만족하지 못하면 환경변수와 후속 결정을 통해 교체합니다.
  - thinking과 streaming은 끄고 `temperature=0.2`, `top_p=0.8`, `max_tokens=512`로 호출합니다.
  - AI에 전달하는 Slack 공지 본문은 최대 12,000자로 제한합니다. 초과하면 임의로 잘라 분석하지 않고 실패로 처리합니다.
  - 요청 제한 시간은 45초로 정합니다. 최초 호출을 포함해 최대 3회 시도하고, 재시도 전 2초와 8초를 기다립니다. 서버가 `Retry-After`를 제공하면 그 값을 우선합니다.
  - 연결 오류, 시간 초과, HTTP 429·5xx와 D-011의 응답 검증 실패만 재시도합니다. 인증·권한 오류와 그 밖의 4xx는 즉시 실패로 처리합니다.
  - 최종 실패한 공지는 D-011에 따라 `processing_failed`로 기록하고 체크리스트와 DM을 만들지 않습니다. 운영자가 실패 목록을 조회하고 선택한 공지를 다시 처리할 수 있도록 서비스 계층에 조회·재처리 기능을 둡니다.
  - 재처리에 성공하면 같은 공지를 새로 만들지 않고 기존 공지 상태를 `processed`로 변경한 뒤 체크리스트를 생성합니다.
- 이유: 형식이 짧고 정해진 추출 작업을 일관되게 수행하면서 일시적인 외부 장애와 영구적인 설정 오류를 구분하기 위함입니다.

## D-019 — 공지 채널 ID와 Slack 원문 링크

- 날짜: 2026-09-14
- 상태: 확정
- 내용:
  - Socket Mode로 메시지 이벤트가 전달된 채널 중 `.env`의 `SLACK_NOTICE_CHANNELS`에 ID가 등록된 채널만 처리합니다. Slack 이벤트가 전달되는 것을 봇이 해당 채널에 접근할 수 있다는 조건으로 사용합니다.
  - 채널 이름은 변경될 수 있으므로 `SLACK_NOTICE_CHANNELS`에는 `C` 또는 `G`로 시작하는 채널 ID만 허용합니다.
  - SeulSeul 자신이 작성한 메시지는 Bolt context의 봇 사용자 ID·봇 ID를 메시지 작성자 ID·봇 ID와 비교해 제외합니다. 두 ID를 별도 환경변수로 두지 않습니다.
  - 사용자에게 공지 원문 전체를 다시 보여 주지 않습니다. `chat.getPermalink`로 얻은 Slack 원문 링크를 제공해 사용자가 원본 위치로 이동하게 합니다.
  - 원문 링크를 가져오지 못하면 해당 메시지를 공지로 저장하지 않고 원문을 제외한 식별 정보와 오류만 로그에 남깁니다.
- 이유: 설정하지 않은 채널의 메시지와 원문에 포함된 개인정보가 사용자 응답에 노출되는 일을 막고, 사용자가 필요할 때 Slack의 원래 문맥을 직접 확인할 수 있게 하기 위함입니다.
