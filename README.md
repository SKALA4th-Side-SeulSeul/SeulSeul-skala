# SeulSeul

Slack 공지의 제출 링크를 학생별 체크리스트로 만들고, 최초 개인 DM 메시지를 계속 갱신하는 Slack 봇입니다. 별도의 마감 알림이나 실제 제출 여부 자동 확인은 제공하지 않습니다.

## 개발 시작

Python 3.11을 사용합니다.

```bash
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
cp .env.example .env
```

`.env`에 개발용 `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `DATABASE_URL`을 채운 뒤 PostgreSQL과 마이그레이션을 준비합니다.

```bash
docker compose up -d postgres
.venv/bin/alembic upgrade head
```

로컬에서는 PostgreSQL만 Docker로 실행하고 Python 앱은 `.venv`에서 실행합니다. 개발 DB를 멈출 때는 데이터 볼륨을 보존하도록 `docker compose down`을 사용하며, 데이터 초기화가 목적이 아니면 `-v`를 붙이지 않습니다.

Slack 앱 설정은 `slack-manifest.yaml`을 기준으로 맞춥니다. `users:read` 같은 OAuth scope를 새로 적용했다면 워크스페이스에 앱을 다시 설치한 뒤 갱신된 Bot Token을 `.env`에 반영합니다.

가입 시 Slack 프로필의 **성명**을 `4기_광주_<1~4>반_<이름>` 형식으로 설정하고 `/seulseul 시작`을 실행합니다. 소속은 성명(`profile.real_name`)으로 판별하며, 표시 이름은 자유롭게 사용할 수 있습니다. 기존 가입자도 같은 명령으로 성명과 반을 갱신할 수 있습니다.

운영 서버에서는 `compose.prod.yaml`을 사용합니다. 운영 절차와 보안 기준은 `docs/DB-TODO.md`를 따릅니다.

## 운영 서버 간편 명령

DBeaver 접속은 [현재 상태와 SSH 터널 절차](docs/DB-ACCESS.md)를 따릅니다. 저장소 Compose는 `127.0.0.1:5432`, 사용자가 접속에 성공한 서버 안내는 `127.0.0.1:15432`여서 아직 일치하지 않습니다. 재배포 전에 서버 변경을 확인하며, 어떤 포트든 외부 인터페이스에 공개하지 않습니다. SSH 계정·인증 및 조회 전용 DB 권한은 실제 설정 확인이 필요합니다.

서버의 `seulseul` 계정으로 직접 로그인한 뒤 `~/app`에서 실행합니다. 아래 스크립트는 **운영 전용**이며 항상 `compose.prod.yaml`을 사용합니다. Rootless Docker 연결을 확인하며 Docker 설치·방화벽 변경·DB 외부 포트 공개는 하지 않습니다. 로컬 개발 봇 실행에는 사용하지 마세요.

| 명령 | 동작 |
| --- | --- |
| `./run.sh setup` | `.env`가 없을 때만 권한 600으로 템플릿 생성. 기존 설정은 보존 |
| `nano .env` | 운영 환경변수 직접 편집. `APP_ENV=production`, `AI_PROVIDER=nvidia`, DB 주소 `postgres:5432` |
| `./run.sh` | 이미지 빌드 → 기존 봇 중지 → DB healthy 대기 → 마이그레이션 → 봇 하나 재생성 |
| `./run.sh postgres` | PostgreSQL만 실행·healthy 대기 |
| `./run.sh migrate` | 빌드·봇 중지·DB 준비·마이그레이션. 봇은 중지 상태 유지 |
| `./stop.sh` | 봇과 DB 순서대로 중지, 컨테이너·데이터 볼륨 보존 |
| `./stop.sh bot` | 봇만 중지, DB 유지 |
| `./stop.sh postgres` | DB 중지 전 의존하는 봇도 중지 |
| `./view.sh` | 전체 컨테이너 상태 (`ps -a`) |
| `./view.sh logs` | 봇 최근 100줄 및 실시간 로그 |
| `./view.sh logs postgres` | PostgreSQL 로그 |
| `./view.sh logs all` | 봇·DB 로그 함께 보기 |
| `./view.sh db` | 기본 읽기 전용 psql 접속. 종료는 `\q` |
| `./view.sh schema` | DB 테이블 목록 |
| `./view.sh config` | 환경변수 값을 출력하지 않고 Compose 구성 검증 |
| `./backup.sh` | 운영 DB custom-format 백업·아카이브 해독 검사·SHA-256 생성. 기존 백업 보존 |
| `./backup_run.sh` | 매일 한국 시간 03:00 자동 백업 등록·재등록 (systemd 사용자 타이머) |
| `./backup_stop.sh` | 자동 백업 예약 해제. 실행 중인 백업·기존 백업·DB 유지 |

각 스크립트의 `--help`로 사용법을 확인할 수 있습니다. 스크립트 위치를 기준으로 실행하므로 다른 작업 디렉터리에서 절대 경로로 실행해도 같은 프로젝트를 사용합니다.

### 운영 DB 백업

자동 실행은 Ubuntu 운영 서버의 `seulseul` 계정으로 직접 로그인해 `./backup_run.sh`를 실행합니다(`sudo`로 실행하지 않습니다). 같은 명령을 반복해도 타이머는 하나만 유지됩니다. 서버에서 Rootless Docker와 PostgreSQL이 실행 중이어야 합니다. 사용자 기본 소켓 `/run/user/<UID>/docker.sock`을 사용하며 로컬 개발 Docker에는 예약하지 않습니다.

- 로그아웃·재부팅 후에도 실행하려면 사용자 lingering이 필요합니다. 꺼져 있으면 등록을 중단하고 `sudo loginctl enable-linger seulseul`을 관리자 계정에서 실행하도록 안내합니다.
- 매일 **03:00 Asia/Seoul**에 실행합니다. 서버가 꺼져 놓친 예약은 다시 켜졌을 때 한 번 보충합니다. 실행 중에는 같은 타이머 백업이 중복 실행되지 않습니다. 수동 `./backup.sh`와는 별개이므로 함께 실행하지 마세요.
- 해제: `./backup_stop.sh`. 타이머만 중지·비활성화하며 진행 중인 백업은 끝까지 실행합니다. 다시 등록하면 예약을 재개합니다. 미실행 기간의 보충 백업이 즉시 실행될 수 있습니다.
- 예약 확인: `systemctl --user list-timers --all seulseul-db-backup.timer`
- 결과·오류 확인: `journalctl --user -u seulseul-db-backup.service -n 100 --no-pager`
- 실패 시 로그에 기록하며 별도 알림·자동 재시도는 없습니다. 다음 예약에 다시 시도합니다. 기존 백업 자동 삭제·외부 업로드도 하지 않으므로 디스크 용량을 확인하고 외부 보관은 별도로 설정하세요.
- 예약 백업의 호스트 실행은 30분으로 제한하고 종료 대기는 30초입니다. 설정 변경 후 `./backup_run.sh`를 다시 실행해야 적용됩니다. 호스트의 Docker 명령 종료가 컨테이너 내부 `pg_dump` 종료까지 보장하지는 않으며 강제 종료 시 불완전한 파일이 남을 수 있습니다. 시간 초과 로그가 있으면 컨테이너 작업·파일을 점검하고 성공한 백업으로 사용하지 마세요. 수동 `./backup.sh`에는 이 systemd 제한이 적용되지 않습니다.
- 관리 파일은 `~/.config/systemd/user/seulseul-db-backup.service`와 `.timer`입니다(`XDG_CONFIG_HOME` 설정 시 해당 경로). 저장소를 옮겼다면 새 위치에서 다시 등록하세요. 스크립트가 만든 파일만 갱신하며 같은 이름의 수동 작성 파일은 덮어쓰지 않습니다.

서버에서 PostgreSQL이 실행 중일 때 `./backup.sh`를 실행합니다. 봇을 끄거나 마이그레이션을 실행하지 않으며, DB 컨테이너와 같은 버전의 `pg_dump --format=custom`을 사용합니다. 기본 위치는 저장소 상위의 `backups`로, `~/app`에서는 `~/backups/seulseul-UTC시각-고유문자열/database.dump`에 저장됩니다. 출력된 경로를 확인하세요.

- 디렉터리는 700, 파일은 600 권한입니다. 비밀번호를 명령 인자에 넣거나 `.env`를 셸로 실행하지 않습니다.
- `pg_dump` 성공·빈 파일 여부 확인 후 `pg_restore --file=/dev/null`로 SQL을 실행하지 않고 전체 아카이브를 해독합니다. 성공한 경우에만 `.partial`을 제거하고 `database.dump`와 `SHA256SUMS`를 남깁니다. 이것은 **실제 복구 시험을 대신하지 않습니다**.
- 실패 시 이번 실행에서 만든 불완전한 파일만 정리하고 비정상 종료합니다. 기존 백업 자동 삭제·보존기간 정리·DB 볼륨 삭제는 하지 않습니다.
- 단일 DB의 스키마·데이터·권한 정보를 백업합니다. PostgreSQL 클러스터 역할·비밀번호·서버 설정·Slack/AI 토큰은 포함하지 않으므로 별도 안전한 보관이 필요합니다. 역할이 없는 격리 DB에 복구할 때는 `pg_restore --no-owner --no-acl` 사용 여부를 검토하세요.
- 덤프에는 학생 개인정보와 공지 내용이 포함될 수 있습니다. Git·채팅에 올리지 말고 서버 밖의 접근 제한된 저장소에도 별도 복사하세요. 주기 실행은 위 타이머로 등록하며 보존 기간 정리·외부 저장소 업로드는 아직 자동화하지 않았습니다.
- 마이그레이션 전에는 `./backup.sh`가 성공한 것을 확인하고 `./run.sh`를 실행합니다. `run.sh`가 백업을 자동 실행하는 것은 아닙니다.

- 최초 준비: `./run.sh setup` → `nano .env` → `./view.sh config` → `./run.sh` → `./view.sh logs`.
- 코드 업데이트: 커밋·푸시된 코드를 서버에서 `git pull --ff-only origin main`으로 받은 뒤 `./run.sh` 실행. 자동 pull은 하지 않습니다. 운영 데이터가 있으면 먼저 백업하세요.
- `.env` 수정도 `./run.sh`로 재생성해야 반영됩니다. 템플릿 생성만으로는 실행할 수 없으며 API 키는 `NVIDIA_API_KEY`, 대기 시간은 `AI_TIMEOUT_SECONDS=45`에 입력합니다. 비밀번호 변경은 기존 DB 계정에 자동 반영되지 않습니다.
- `run.sh`/`stop.sh`를 동시에 실행하지 마세요. 동일 Slack 앱의 로컬 봇은 먼저 종료합니다. 마이그레이션 실패 시 운영 봇은 중지 상태로 남으므로 원인 해결 후 다시 `./run.sh`를 실행하세요.
- 로그 보기에서 `Ctrl+C`는 봇을 중지하지 않습니다. 컨테이너 시작은 Slack 연결 성공을 보장하지 않으므로 로그 확인이 필요합니다. 로그에는 기존 오류로 노출된 키·개인정보가 있을 수 있어 공유 전 가려야 합니다.
- `view.sh db`는 기본 읽기 전용 옵션이지 권한이 제한된 별도 DB 계정은 아닙니다. 임의로 쓰기 설정을 해제하지 마세요. DB 포트는 외부에 공개하지 않습니다.
- 스크립트는 운영 서버에서 직접 검증해야 합니다. 자동 테스트는 가짜 Docker로 명령 순서·실패 시 중단·데이터 보존을 검증하며 실제 컨테이너를 조작하지 않습니다.

## 최초 연결 후 계속 갱신하는 개인 체크리스트

해지 성공 시에는 임시 응답 대신 **일반 DM**으로 `SeulSeul 해지가 완료되었습니다`를 보냅니다. 이 안내도 다음 시작·해지 명령에서 정리됩니다. 정상 시작은 체크리스트만 보내며 별도 가입 완료 안내를 보내지 않습니다. 성명 형식 오류는 아래 안내 예외입니다. 코드 변경 후에는 기존 봇을 종료하고 한 프로세스만 재실행해야 구버전 응답이 섞이지 않습니다.

학생이 입력하는 명령은 `/seulseul 시작`, `/seulseul 해지`뿐입니다. 슬래시 명령에는 빈 수신 확인만 보내며 임시 메시지를 보내지 않습니다. 체크리스트는 봇과 학생의 **일반 DM**으로 전달됩니다. 성명 형식이 잘못되면 수정 방법을 일반 DM으로 보내고 기존 가입·완료 기록은 유지합니다. 성명 조회 자체의 실패·권한 오류 등은 로그에서 확인합니다. 체크리스트 버튼의 오류 안내는 기존처럼 유지합니다.

실행 전 다음 설정을 적용합니다.

1. 봇이 초대된 자동 수집 채널은 `.env`의 `SLACK_NOTICE_CHANNELS`에, 봇을 초대할 수 없어 운영자 CLI로만 처리할 채널은 `SLACK_MANUAL_NOTICE_CHANNELS`에 지정합니다. 두 목록의 채널 대상을 `SLACK_NOTICE_TARGETS`에 모두 적습니다. `all`은 등록된 광주 학생 전체, `1`~`4`는 해당 반입니다. 아래는 가상 ID 예시이며 실제 값으로 바꿉니다.

   ```dotenv
   SLACK_NOTICE_CHANNELS=C0000000001,G0000000002,C0000000003
   SLACK_MANUAL_NOTICE_CHANNELS=C0000000099
   SLACK_NOTICE_TARGETS=C0000000001=all,G0000000002=all,C0000000003=3,C0000000099=all
   ```

2. `slack-manifest.yaml`의 `chat:write`, `im:write`, `im:history` 권한과 명령 안내를 Slack 앱에 반영하고 재설치합니다. 토큰이 바뀌었다면 `.env`도 갱신합니다.
3. 봇을 멈춘 상태에서 마이그레이션 후 다시 실행합니다. 기존 학생·공지·완료 상태는 유지하고 필요한 발송 기록과 원본 이벤트 상태 테이블을 준비합니다. 최초 한 번 발송 정책(D-025)은 기존 스키마를 재사용하므로 별도 마이그레이션은 없습니다.

   ```bash
   .venv/bin/alembic upgrade head
   .venv/bin/python -m seulseul.main
   ```

- `/seulseul 시작`을 실행하면 본인과 봇의 개인 DM에서 기존 봇 일반 메시지를 정리하고 체크리스트 하나를 새로 보냅니다. 완료 기록은 유지하고 목록 필터·페이지는 초기화합니다. 이후 날짜 변경·봇 재시작에는 같은 메시지만 갱신합니다. 매일 정시 발송은 하지 않습니다. 봇은 단일 프로세스로 상시 실행해야 합니다.
- 기본 목록은 본인에게 배정된 **마감 전·미삭제·미완료** 항목입니다. 마감이 빠른 순으로 5개씩 하나의 테두리 카드 안에 표시합니다. `📝`는 폼, `📄`는 문서이며 굵은 할 일 제목을 누르면 제출 링크로 이동합니다. 제목은 화면에서만 최대 28자로 줄이고 긴 요약은 목록에서 숨기며 원래 데이터는 보존합니다.
- 제목 아래에는 도메인·`MM/DD HH:MM 마감 · 원문`을 작은 보조 정보로, 오른쪽에는 `✓` 버튼을 표시합니다. **실제 제출 후** `✓`를 눌러 완료하고, 카드 아래의 `완료 보기 (개수)`로 전환한 뒤 `↶`로 취소할 수 있습니다. 마감과 갱신 시각은 `Asia/Seoul`입니다. 최신 컨테이너 블록을 받지 못하는 워크스페이스에서는 일반 블록 레이아웃으로 표시합니다.
- **완료 목록에는 미완료 공지가 표시되지 않습니다.** 새 공지는 미완료로 배정되며 `미완료 보기 (개수)` 버튼으로 전환하면 볼 수 있습니다. 작은 문구로 현재 목록·개수를 표시하고 새로고침과 날짜 변경에도 선택한 목록을 유지합니다.
- 새 공지 분석 성공, 가입, 완료·취소 시 갱신 작업을 깨웁니다. 기본 30초 주기 검사로 CLI 재처리 성공, 마감 경과, 최초 발송 복구도 반영합니다. 이 주기는 정시 알림이 아니라 기존 메시지 동기화용입니다.
- 가입하면 마감 전 기존 공지도 배정합니다. 가입 학생의 성명에서 반 번호가 바뀌면 `user_change` 이벤트로 해당 학생의 현재 성명만 조회하고 소속을 갱신합니다. 기존 DM에서 이전 반 항목은 숨기고 새 반과 전체 공지의 유효 항목을 표시하며 완료 기록은 유지합니다. `/seulseul 시작` 재입력이나 별도 안내 DM은 필요 없습니다. 이름만 바뀌면 성명만 갱신하고 같은 이벤트가 중복돼도 DM을 새로 만들지 않습니다.
- 적용: 봇 코드를 반영하고 Slack 앱의 **Event Subscriptions → Subscribe to bot events**에 `user_change`를 추가한 뒤 저장하세요(`slack-manifest.yaml` 반영). 기존 `users:read` 권한을 사용하며 새 권한은 추가하지 않습니다. 앱 설치에 해당 권한이 없다면 권한 반영·재설치가 필요합니다. DB 마이그레이션은 없습니다.
- 미가입·해지한 학생의 이벤트는 무시합니다. 늦게 도착한 이벤트 본문의 성명 대신 현재 프로필을 조회하며, 같은 학생의 가입·해지·동기화를 직렬화하고 기존 학생 행만 갱신합니다. 조회 실패나 잘못된 성명은 로그에 남기고 마지막 정상 정보를 유지합니다. 이번 범위는 정상 형식의 반 변경이며, 형식 오류 자동 중지·누락 이벤트 전체 재수집은 제공하지 않습니다. 실패·중단 중 놓친 변경은 이후 프로필 이벤트 또는 `/seulseul 시작`으로 다시 동기화할 수 있습니다.
- 체크리스트 버튼은 현재 사용 중인 본인 발송 기록 ID·DM 채널·메시지 ts가 모두 정확히 일치해야 처리합니다. 다른 기록의 ID를 주소로 보정하거나 ts를 숫자로 변환하지 않습니다. 과거의 다른 메시지·타인·삭제·마감 항목은 변경할 수 없습니다. 일반 동기화와 버튼 검증 모두 주소가 저장된 가장 이른 메시지를 사용하며, `/seulseul 시작`은 기존 봇 메시지를 정리한 뒤 하나의 새 메시지를 만듭니다.
- 해지하면 개인 DM의 기존 봇 일반 메시지를 정리한 뒤 학생·개인 체크리스트·발송 기록을 DB에서 삭제합니다. 학생 메시지·다른 봇 메시지·공지 채널은 변경하지 않으며, ‘나에게만 표시’ 임시 응답은 삭제 대상이 아닙니다.
- 메시지 정리에 실패하면 명령을 완료하지 않고 자동 DM 갱신을 중지합니다. 권한·연결 문제를 해결하고 같은 명령을 다시 실행하면 남은 메시지를 정리합니다. 부분 삭제는 복원하지 않습니다. 정리 상태는 기존 발송 기록의 `uncertain`/`dm_cleanup_pending`으로 보관하므로 마이그레이션은 필요 없습니다(D-026).
- 전송이 명확히 실패하면 지연 후 다시 시도합니다. 첫 전송 후 응답 유실·프로세스 중단으로 성공 여부가 불명확하면 `daily_checklist_messages.status=uncertain`으로 기록하며 **자동 재발송하지 않습니다**. 로그의 `delivery` ID와 Slack 메시지 존재 여부를 운영자가 대조해야 합니다. 결과 확인 없이 상태를 초기화하면 중복 DM이 생길 수 있습니다.
- 기존 메시지를 Slack에서 삭제하면 자동으로 새 메시지를 보내지 않고 편집 실패를 기록합니다. 운영자가 기록을 확인해야 합니다. 과거 테이블·내부 모델의 `daily` 이름과 생성일 컬럼은 호환성을 위해 유지되지만 날짜별 발송에는 사용하지 않습니다.
- 공지 수정·링크 변경·삭제도 아래 규칙에 따라 최초 메시지에 반영합니다.

이미 `im:history`를 포함한 현재 manifest 권한을 설치했다면 화면 변경만으로 재설치할 필요는 없습니다. 아직 해당 권한이 없다면 위 설정 절차대로 권한 반영 후 재설치합니다.

### 체크리스트 버튼 오류 로그 확인

`현재 연결된 본인의 체크리스트에서만 변경할 수 있습니다.`는 여러 검증 실패에 공통으로 쓰이는 안내입니다. 이 문구만으로 해지·중복 기록·구버전 실행을 원인으로 확정하지 않습니다. 진단 로그는 기본 INFO 설정에서 출력되며, 수정 코드를 실행하는 봇을 재시작해야 나타납니다.

버튼 오류·갱신 대기 안내에는 `replace_original=false`, `delete_original=false`를 명시합니다. 별도 임시 안내가 기존 체크리스트를 교체·삭제하지 않게 하는 조치입니다([Slack 응답 규칙](https://docs.slack.dev/interactivity/handling-user-interaction/)). 이전 버전에서 화면이 사라졌다면 정상 화면 복구 후 버튼 검증 원인은 별도로 확인해야 합니다.

- 로컬: 기존 봇을 종료한 뒤 `.venv/bin/python -m seulseul.main`으로 실행하고 해당 터미널에서 확인합니다.
- 운영: 수정 코드가 서버에 반영된 뒤 `./run.sh`로 이미지를 빌드·재생성하고 `./view.sh logs bot`으로 확인합니다. 로컬 미커밋 수정은 서버의 `git pull`로 전달되지 않습니다. 진단 로그에 새 환경변수·권한·마이그레이션은 필요 없습니다.
- 로그 보기를 켜고 `/seulseul 시작` → 체크리스트 버튼 한 번 클릭 순으로 재현합니다. 첫 DM의 `checklist_delivery_saved`와 클릭의 `checklist_action_received` → `checklist_action_parsed` → `checklist_message_validation` → 결과를 대조합니다.

각 클릭의 `trace_id`는 핸들러·서비스·저장소에서 동일합니다. `instance_id`와 `pid`는 처리 프로세스를 구분하며 재시작하면 `instance_id`가 바뀝니다(커밋 버전이 아닙니다). `diagnostic_version=1`은 새 진단 로그 형식이 적용됐다는 표시입니다. 새 이벤트 로그가 없다면 재시작/배포 반영·보고 있는 로그·다른 봇 프로세스의 이벤트 수신 여부부터 확인합니다.

같은 Slack 앱을 운영 서버와 로컬에서 동시에 실행하지 마세요. [Socket Mode는 여러 연결에 이벤트를 분배](https://docs.slack.dev/apis/events-api/using-socket-mode/#using-multiple-connections)하므로, 시작 명령을 처리한 봇과 버튼을 처리한 봇이 달라질 수 있습니다. 서로 다른 DB를 사용하면 버튼을 받은 쪽에 해당 발송 기록이 없을 수 있습니다. 로컬의 `pgrep -f 'seulseul[.]main'`으로 후보 PID를 찾고, 실행 명령·작업 폴더가 이 프로젝트인지 확인한 뒤 불필요한 봇만 종료하세요. 로컬 Docker·다른 컴퓨터의 봇도 별도로 확인해야 하며, PID 존재만으로 같은 Slack 앱 연결을 확정하지 않습니다.

`checklist_message_validation`의 `result=rejected`일 때 `reason`을 확인합니다. `result=payload_match`는 검증 성공입니다. 이전 버전의 `address_fallback` 보정 처리는 제거했습니다.

| `reason` | 뜻 |
| --- | --- |
| `delivery_not_found` | 버튼의 발송 기록 ID가 현재 DB에 없음 |
| `delivery_owner_mismatch` | 발송 기록은 있지만 클릭한 학생의 기록이 아님 |
| `delivery_not_current` | 본인 기록이지만 현재 동기화에 사용하는 메시지가 아님 |
| `channel_mismatch` | 저장된 DM 채널과 버튼에서 받은 채널이 다름 |
| `timestamp_mismatch` | 채널은 같지만 저장된 메시지 시각과 버튼의 메시지 시각이 다름 |

`payload_daily_id`, `matched_daily_id`, `stored_message_ts`, `received_message_ts`, `channel_matches`, `timestamp_matches`, `record_status`를 함께 기록합니다. 거부 시 해당 학생의 발송 기록 표본(`student_records_sample`, 최신 생성일 기준 최대 3건)도 남겨 기록 재생성·누락을 대조합니다. `checklist_delivery_save_conflict`와 `rows_updated=0`은 Slack 응답 후 발송권에 해당하는 DB 기록 갱신이 적용되지 않았다는 뜻입니다.

`checklist_action_result`의 `saved=true`는 상태 변경이 저장됐다는 뜻이며 `dm_synchronized=false`면 화면 갱신은 보류/실패한 상태입니다. Slack 사용자·워크스페이스·채널 식별자는 해시 참조(`*_ref`)로 출력합니다. 성명·공지 본문·버튼 원문·토큰·응답 URL·DB 접속 문자열·예외 본문은 새 진단 로그에 넣지 않습니다. 공유할 때는 위 `checklist_*` 이벤트만 추려 전달하세요.

## 공지 수정·링크 변경·삭제

- 기존 공지의 본문을 수정하면 유지된 링크별로 AI를 다시 호출합니다. 성공한 제목·요약·마감일을 반영하며 학생별 완료 상태는 유지합니다. 분석 실패 시 마지막 성공 분석을 유지하고 최신 원문·실패 원인을 저장하므로 운영자 재처리가 가능합니다.
- 추가된 링크는 원본별 공지로 저장합니다. 같은 링크가 다른 반에 올라오면 그 반에도 배정하고, 학생 화면에서는 링크당 한 항목만 표시합니다. 반 공지와 전체 공지가 겹치면 유효한 반 공지를 우선하고 같은 우선순위에서는 최신 게시 원본을 사용합니다. 제목·마감일·원문 링크는 선택된 원본을 따릅니다.
- 원본의 링크 제거·삭제·마감 경과 후 다른 유효한 대상 원본이 있으면 그 원본으로 전환하고, 없으면 숨깁니다. 원본 전환 시 체크리스트 ID와 완료 기록은 유지합니다. 분석 성공 이력이 없는 원본은 표시하지 않습니다.
- 같은 원본에 제거했던 링크를 다시 넣으면 분석 성공 후 기존 항목과 완료 상태를 복구합니다. 재분석 실패 시 옛 분석으로 복구하지 않으며, 이후 CLI 재처리 성공 시 복구할 수 있습니다.
- 원문을 삭제하면 연결된 공지·체크리스트를 모두 삭제 상태로 바꿉니다. 물리 삭제는 하지 않으며, 원문 링크 조회나 AI 호출 없이 기존 DM을 갱신합니다. 삭제한 항목의 기존 버튼으로는 완료 상태를 바꿀 수 없습니다.
- 본문이 그대로인 메타데이터 변경은 AI를 호출하지 않습니다. `notice_sources`가 원본별 최신 이벤트 시각과 삭제 여부를 기억해 중복·역순 이벤트 및 늦게 끝난 분석이 최신 내용을 덮어쓰는 것을 막습니다.
- AI 분석 중 프로세스가 종료되면 `notice_sources.applied=false`가 남을 수 있습니다. 아래 `pending` 명령으로 확인합니다. 같은 이벤트가 다시 전달되면 재처리할 수 있고, 미전달 시 원문을 다시 수정해 새 이벤트를 발생시켜야 합니다. 누락 이벤트의 자동 조회·복구는 아직 제공하지 않습니다.
- 기존 `message.channels`·`message.groups` 구독을 사용하므로 이번 변경을 위해 권한이나 manifest를 추가하지 않습니다. [Slack 수정 이벤트](https://docs.slack.dev/reference/events/message/message_changed/)와 [삭제 이벤트](https://docs.slack.dev/reference/events/message/message_deleted/) 형식에 맞춰 원본 식별자를 검증합니다.

원본 동기화를 적용할 때는 DB를 백업하고 봇을 중지한 뒤 마이그레이션 후 다시 시작합니다. 최신 revision은 `d94132ac684e`입니다. 운영에서는 새 코드의 `./run.sh`가 빌드·봇 중지·마이그레이션·재시작을 수행합니다. 학생별 링크 키를 기존 데이터로 채우며 완료 기록은 보존합니다. 다중 원본 저장 후 downgrade는 자동 데이터 삭제 대신 거절됩니다.

과거에 중복으로 건너뛴 다른 반 공지의 본문·링크는 DB에 없습니다. 새 버전 적용 후 누락된 원본을 실제로 편집하거나 재게시하여 새 이벤트로 수집하세요. 새로고침·재가입만으로 과거 원본을 복구하지 않으며 Slack 기록 전체를 자동 수집하지 않습니다.

동일 링크의 실패 공지가 여러 개면 재처리에 `--channel-id`와 `--message-ts`를 지정합니다. `python -m seulseul.notices.retry list`가 원본 선택 인자를 포함한 명령을 출력합니다. URL만으로 원본이 여러 개 조회되면 임의의 공지를 수정하지 않고 중단합니다.

## AI 분석 실패 공지 재처리

일시적 연결 실패·시간 초과·HTTP 429/5xx 및 일시적 원문 링크 조회 실패는 최초 처리 후 **5분 → 15분 → 1시간** 간격으로 최대 3회 추가 자동 재처리합니다(각 실패 완료 시점부터의 간격). 기존 짧은 분석 재시도는 유지하므로 한 자동 처리에서도 AI 요청이 최대 3번 발생할 수 있습니다. 내용·날짜·저장 규격 오류, 인증/권한·그 밖의 4xx, 예상 밖 내부 오류는 지연 자동 재처리하지 않습니다. 한도를 소진하면 실패 기록과 로그를 남기며 CLI로 확인합니다. 수정 분석 실패 시 마지막 성공 분석·완료 기록은 유지합니다.

단일 운영 봇의 별도 30초 주기 작업이 예약을 확인하므로 체크리스트 동기화를 막지 않습니다. 서버가 꺼져 있으면 재기동 후 지난 예약을 처리합니다. `next_retry_at`과 `retry_count`에 예약과 지연 처리 횟수를 저장하며 DB 구조 변경은 없습니다. 실행 전에 횟수·다음 예약을 갱신하므로 처리 중 강제 종료도 1회를 소비하고 마지막 차례 중 종료되면 수동 확인이 필요합니다. 여러 봇 프로세스 동시 운영·외부 호출의 정확히 한 번 실행은 보장하지 않습니다.

이번 버전 이전 실패 행은 자동 오류 분류가 없으므로 소급 예약하지 않습니다. 예약이 없는 실패 행은 CLI로 재처리할 수 있고, 수동 재처리의 AI 분석이 다시 일시 장애로 실패하면 새 자동 재처리 예산을 시작합니다. 수동 permalink 조회 단계에서 실패하면 기존 횟수·예약·실패 기록을 유지합니다. 같은 원본 이벤트는 중복 처리를 생략하지만 같은 링크라도 새 메시지로 재게시하면 D-027에 따라 새 원본으로 분석합니다. `list`에 다음 예약과 횟수를 표시합니다. 예약 표시 시각은 저장된 시간대 기준입니다.

운영 Docker 환경에서는 프로젝트 루트의 `./retry.sh`로 실패 공지를 조회·재처리할 수 있습니다. 인자 없이 실행하면 목록만 조회하며, `retry`를 명시해야 AI를 호출합니다. 이 스크립트는 두 번째 봇을 시작하지 않고 일회성 운영 컨테이너에서 CLI를 실행합니다.

```bash
./retry.sh list
./retry.sh pending
./retry.sh retry --workspace-id '<워크스페이스 ID>' --url '<제출 링크>' --channel-id '<채널 ID>' --message-ts '<메시지 ts>'
```

직접 Docker Compose 명령을 사용해야 한다면 다음과 같이 실행합니다.

```bash
docker compose -f compose.prod.yaml exec -T bot python -m seulseul.notices.retry list
docker compose -f compose.prod.yaml exec -T bot python -m seulseul.notices.retry pending
docker compose -f compose.prod.yaml exec -T bot python -m seulseul.notices.retry retry --workspace-id '<워크스페이스 ID>' --url '<제출 링크>' --channel-id '<채널 ID>' --message-ts '<메시지 ts>'
```

봇이 중지되어 있고 DB는 실행 중이면 `exec -T bot` 대신 `run --rm --no-deps bot`을 사용합니다. 성공한 분석은 봇을 다시 실행한 후 DM에 반영됩니다. 목록이 출력하는 `python -m ...` 부분의 인자를 복사해 위 운영 명령 뒤에 붙이세요. 운영 호스트에서 `postgres`라는 컨테이너 주소나 `.venv`를 사용하지 않습니다.

로컬 개발 환경에서는 프로젝트 폴더에서 실행합니다.

```bash
.venv/bin/python -m seulseul.notices.retry list
```

목록에 표시된 **재처리 명령**을 복사해 실행하면 해당 공지 하나를 다시 분석합니다.
명령 형식은 다음과 같습니다. URL은 Slack 원문 링크가 아니라 공지에 포함된 제출 링크입니다.

```bash
.venv/bin/python -m seulseul.notices.retry retry --workspace-id '<워크스페이스 ID>' --url '<제출 링크>'
```

- 현재 `.env`/환경변수의 DB·공지 채널·AI 설정을 사용합니다. 설정의 우선순위는 `config.py`를 따릅니다.
- 목록 조회는 AI를 호출하지 않습니다. 기본 20건이며 `--limit 100`, `--workspace-id`로 조정합니다.
- 성공하면 기존 공지를 갱신하고 오류를 지웁니다. 다시 실패하면 최근 오류를 저장합니다.
- 수신한 생성·수정 이벤트로 저장된 최신 원문과 원래 게시 시각을 사용합니다. CLI가 Slack 원문을 별도로 조회하지는 않습니다.
- 이미 성공했거나 삭제된 공지, 현재 설정에서 제외된 채널의 공지는 재처리하지 않습니다.
- Slack 원문 링크 조회에 실패한 공지도 실패 목록에 보관합니다. 선택 재처리 때만 저장된 채널·메시지 ts로 permalink를 다시 가져오고 AI 분석을 진행합니다. 목록 조회는 Slack API를 호출하지 않습니다. 조회 권한·원문 존재 여부가 해결되지 않았다면 실패 상태가 유지됩니다.
- 재처리에 성공하면 실행 중인 봇의 주기 작업이 배정하고 기존 DM을 갱신합니다. 시간대에 따른 대기 없이 반영하며, 위 최초 설정 이후 재처리할 때마다 앱을 재설치할 필요는 없습니다.
- 학생용 Slack 재처리 명령은 제공하지 않습니다.

`pending`은 `notice_sources.applied=false` 원본의 워크스페이스·채널·메시지 ts를 읽기 전용으로 표시합니다. 정상 분석 중인 원본도 포함되므로 잠시 후 재확인합니다. DB에 해당 이벤트 본문이 없어서 자동 재처리하지 않으며, 계속 남은 항목은 Slack 원문을 실제 수정해 새 이벤트를 발생시키세요. 삭제된 원본은 운영자가 별도로 상태를 확인해야 합니다. 이 명령은 AI 실패 행의 `list`·`retry`와 다릅니다.

## 운영자 수동 공지 처리

봇을 초대할 수 없는 `4기_교육생_전체공지` 채널의 공지나 자동 분석 실패 공지는 운영자 CLI로 처리합니다. 운영자는 Slack 원문 permalink와 원문 파일을 전달하며, CLI는 기존 공지 서비스·중복 판정·학생별 DM 갱신을 재사용합니다. 학생이 Slack에서 실행하는 명령은 추가하지 않습니다.

```bash
python -m seulseul.notices.manual add \
  --workspace-id '<워크스페이스 ID>' \
  --source-url 'https://workspace.slack.com/archives/C.../p...' \
  --text-file notice.txt

python -m seulseul.notices.manual edit \
  --workspace-id '<워크스페이스 ID>' \
  --source-url 'https://workspace.slack.com/archives/C.../p...' \
  --text-file notice-edited.txt

python -m seulseul.notices.manual edit \
  --workspace-id '<워크스페이스 ID>' \
  --source-url 'https://workspace.slack.com/archives/C.../p...' \
  --text-file notice.txt \
  --title '설문 참여' \
  --summary '설문을 제출합니다.' \
  --deadline '2026-09-30 23:59' \
  --deadline-source-text '9월 30일 23:59'

python -m seulseul.notices.manual delete \
  --workspace-id '<워크스페이스 ID>' \
  --source-url 'https://workspace.slack.com/archives/C.../p...'
```

`--text-file -`를 사용하면 원문을 표준 입력으로 받을 수 있습니다. 수동 마감일에 시간대가 없으면 `Asia/Seoul`로 해석합니다. 제목·요약·마감일을 모두 입력하면 AI를 호출하지 않으며, 기존 체크리스트 완료 상태는 유지됩니다.

운영 Docker에서는 원문을 표준 입력으로 전달해 일회성 컨테이너로 실행할 수 있습니다.

```bash
cat notice.txt | docker compose -f compose.prod.yaml run --rm --no-deps -T bot \
  python -m seulseul.notices.manual edit \
  --workspace-id '<워크스페이스 ID>' \
  --source-url 'https://workspace.slack.com/archives/C.../p...' \
  --text-file -
```

### 분석 실패로 처리하는 입력

- 본문 12,000자 초과, AI 제목 255자 초과, AI 결과의 NUL 문자는 임의 자르기 없이 분석 실패로 기록합니다.
- 정규화 URL이 UTF-8 기준 2,048바이트를 초과하거나 원문 자체에 NUL이 있으면 공지 행을 안전하게 저장할 수 없어 `processing_failed` 행 대신 미적용 원본(`pending`)으로 남깁니다. 로그의 원문 수정 안내에 따라 URL·원문을 고친 뒤 새 이벤트로 수집하세요. 링크나 원문을 임의로 잘라 저장하지 않습니다.
- AI의 날짜를 그대로 신뢰하지 않고 인용한 원문 표현으로 날짜·시간을 독립 계산해 대조합니다. 지원 예시는 `2026-09-27`, `9/27`, `9월 27일`, 오늘·내일·모레·이번/다음 주 요일과 24시간제·오전/오후 시각입니다. 시간 생략 시 23:59이며 연도·상대 날짜는 원래 Slack 게시 시각 기준입니다.
- 지원하지 않는 날짜나 의미가 모호한 자정·밤·시 반 표현은 실패할 수 있습니다. 원문을 명시적인 날짜·시각으로 바꿔 재분석하세요. 날짜와 시간이 다른 줄에 있으면 AI가 시각까지 함께 인용해야 합니다. 임의로 기한을 만들어 넣지 않습니다.
- `Retry-After` 즉시 대기는 최대 60초만 허용합니다. 상한 초과·비유한 값은 실패로 기록하고, HTTP 429/5xx에서 발생한 경우 지연 자동 재처리 대상으로 예약합니다. 그 밖의 실패는 운영자 선택 재처리를 사용합니다. 예기치 못한 분석기 예외는 예외 종류만 실패 사유로 기록하며 지연 자동 재처리하지 않습니다.

```bash
./scripts/check.sh
```

.venv/bin/python -m ruff check --fix .
.venv/bin/python -m ruff format .
